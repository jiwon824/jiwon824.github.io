트러블슈팅 딥다이브

이력서의 결과 뒤에 있는 문제 인식과 해결 과정입니다. 한계와 남은 과제도 함께 남깁니다.

개별 테스트는 656ms인데 전체는 6분 38초 — 뉴스바라 테스트 종료 지연뉴스바라▸

상황

CI 파이프라인이 지연되어 코드 변경부터 배포 반영까지의 시간이 길어졌습니다. 전체 테스트 실행에 6분 38초가 소요됐습니다.

문제 인식

afterTest 훅으로 개별 테스트 시간을 측정하자 최장 테스트가 656ms에 불과했습니다. 테스트 실행 자체가 아니라 종료 단계가 병목이라는 모순을 발견했습니다.

원인

테스트 본문은 종료됐지만 Redis/Lettuce 재연결 스레드와 Hikari shutdown 로그가 반복되며 JVM 종료가 지연되고 있었습니다. Hibernate ddl-auto가 create-drop이라 컨테이너 종료 이후에도 불필요한 drop 시도가 발생했습니다.

해결

Testcontainers를 Startables.deepStart()로 초기화 순서를 고정하고, AsyncExecutor에 shutdown 대기 정책을 적용했습니다. Redis 테스트 설정의 connect/command/shutdown timeout을 축소해 재연결 시도 지연을 제거하고, Hibernate ddl-auto를 create로 변경했습니다.

결과

6분 38초 → 1분 33초 (약 77% 단축) · 159개(단위 93 + 통합 66) 전체 통과 재검증

한계: 원인 분석과 개선 과정에서 AI의 도움을 받은 비중이 컸습니다. 직접 측정한 범위와 AI에 맡긴 범위, 이후 직접 검증한 부분을 구분해 정리하는 작업을 이어가고 있습니다.
왜 클라이언트를 믿지 않는가 — SQUIZ 서버 중심 채점SQUIZ▸

상황

답안 제출 단계에서 클라이언트가 채점 결과(isCorrect)를 직접 서버로 전달하는 구조였습니다.

문제 인식

요청 값을 조작하면 채점 결과를 임의로 바꿀 수 있어, 추천·복습 서비스의 핵심 신뢰성이 깨질 수 있는 구조였습니다.

해결

클라이언트는 선택한 답안 값만 전달하고, 서버가 이를 Set으로 파싱해 보유한 정답과 비교하는 방식으로 직접 채점하도록 변경했습니다. 이후 요구사항이 문제집 방식에서 연속 퀴즈로 바뀌자, 진행 상태·다음 문제 선택·섹션 접근 규칙까지 서버 중심 API로 재설계했습니다.

부속 설계

현재 복습 상태(user_review_items)와 풀이 이력(user_review_log)을 분리하고, FSRS 알고리즘으로 다음 복습 시점을 계산해 갱신했습니다.

결과

요청 조작으로 채점 결과를 변경할 수 없는 구조 확보

왜 DB 수준인가 — 뉴스바라 멱등성과 저장소 역할 분리뉴스바라▸

상황

하루 한 번 제공되는 오늘의 퀴즈를 같은 날 중복 제출하면, unique 제약 충돌로 500 오류가 발생했습니다.

결정

애플리케이션 레벨에서 예외를 해석해 처리하는 대신 ON CONFLICT DO NOTHING으로 DB 수준에서 멱등 처리해, 하루 한 번의 스트릭 적립을 보장했습니다.

부속 설계

관계와 정합성이 중요한 서비스 데이터는 PostgreSQL, 구조가 유연한 기사 원문은 MongoDB, 추천 후보군·이력 등 실행 상태는 Redis로 저장소 역할을 분리했습니다. Redis 추천 풀은 임시 키에 새 데이터를 채운 뒤 RENAME으로 교체해 교체 과정의 원자성을 확보했고, 후보가 부족하면 DB 조회로 보충하는 fallback 구조를 추가했습니다.

결과

중복 요청·후보 부족 상황에서도 API가 실패하지 않는 안정적 응답 확보

설정의 영속성 ≠ 데이터의 영속성 — 아이다 Prometheus 데이터 유실아이다▸

상황

운영 환경에서 docker compose down/up으로 재배포할 때마다 Prometheus에 쌓인 모니터링 지표가 사라졌습니다.

원인

Prometheus 컨테이너의 TSDB 데이터 경로가 별도 볼륨에 연결돼 있지 않아, 컨테이너 재생성 시 함께 삭제되고 있었습니다. 설정 파일은 이미지·마운트로 영속이지만, 런타임 데이터는 그렇지 않다는 것을 구분하게 된 지점입니다.

해결

Prometheus TSDB 경로를 named volume으로 분리해, 재배포 이후에도 지표 이력이 보존되도록 개선했습니다.

한계: Grafana 대시보드는 구성하지 않아 지표 수집까지만 진행했고, 알림 임계치·시각화는 다루지 못했습니다. k6 테스트도 health endpoint 대상 스모크 테스트(1 VU·5회) 수준이라, 실제 부하·장애 상황에 대한 검증은 진행하지 못했습니다.
