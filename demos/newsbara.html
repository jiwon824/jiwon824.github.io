트러블슈팅 딥다이브

개별 테스트는 656ms인데 전체는 6분 38초 — 테스트 종료 지연▸

상황

CI 파이프라인이 지연되어 코드 변경부터 배포 반영까지의 시간이 길어졌습니다. 전체 테스트 실행에 6분 38초가 소요됐습니다.

문제 인식

afterTest 훅으로 개별 테스트 시간을 측정하자 최장 테스트가 656ms에 불과했습니다. 테스트 실행 자체가 아니라 종료 단계가 병목이라는 모순을 발견했습니다.

원인

테스트 본문은 종료됐지만 Redis/Lettuce 재연결 스레드와 Hikari shutdown 로그가 반복되며 JVM 종료가 지연되고 있었습니다. Hibernate ddl-auto가 create-drop이라 컨테이너 종료 이후에도 불필요한 drop 시도가 발생했습니다.

해결

Testcontainers를 Startables.deepStart()로 초기화 순서를 고정하고, AsyncExecutor에 shutdown 대기 정책을 적용했습니다. Redis 테스트 설정의 connect/command/shutdown timeout을 축소해 재연결 시도 지연을 제거하고, Hibernate ddl-auto를 create로 변경했습니다.

결과

6분 38초 → 1분 33초 (약 77% 단축) · 159개(단위 93 + 통합 66) 전체 통과 재검증

한계: 원인 분석과 개선 과정에서 AI의 도움을 받은 비중이 컸습니다. 직접 측정한 범위와 AI에 맡긴 범위, 이후 직접 검증한 부분을 구분해 정리하는 작업을 이어가고 있습니다.
왜 DB 수준인가 — 멱등성과 저장소 역할 분리▸

상황

하루 한 번 제공되는 오늘의 퀴즈를 같은 날 중복 제출하면, unique 제약 충돌로 500 오류가 발생했습니다.

결정

애플리케이션 레벨에서 예외를 해석해 처리하는 대신 ON CONFLICT DO NOTHING으로 DB 수준에서 멱등 처리해, 하루 한 번의 스트릭 적립을 보장했습니다.

부속 설계

관계와 정합성이 중요한 서비스 데이터는 PostgreSQL, 구조가 유연한 기사 원문은 MongoDB, 추천 후보군·이력 등 실행 상태는 Redis로 저장소 역할을 분리했습니다. Redis 추천 풀은 임시 키에 새 데이터를 채운 뒤 RENAME으로 교체해 교체 과정의 원자성을 확보했고, 후보가 부족하면 DB 조회로 보충하는 fallback 구조를 추가했습니다.
